## 1. 目的、原因与风险

### 1.1 原因（为什么需要本条款）

1. G0 审计实证：p12/p13/p14 三契约"评审门有运行痕迹、实现已合入生效、批准
   记录从未回写"——根因是授权与记录义务没有持久化形式，依赖逐次口头授权，
   团队流程一变即漏。
2. p9/p10 先例证明"用户授权 captain 自主推进"是本仓库已存在的合法授权形态，
   但它以一次性批注形式存在，无范围、无回写义务、无失效条件——本草案把它
   结构化。
3. 逐项请示在多任务并行团队中造成治理与进度的持续张力；把"调度权"授予
   captain、把"批准权"明确保留给用户，可以把张力转化为明确分工。

### 1.2 风险与防线（如实预注册）

1. **风险 A：自主权被误读为批准权**——防线 = §2 末的权限性质声明 + §3 硬
   边界逐项列举 + §4.3 的阻断机制。
2. **风险 B：硬边界被赶进度侵蚀**（沉默/既成事实被当作批准）——防线 =
   §3.末段"沉默不构成批准"重申 + §4.4 审计触发义务 + §5.1.b 的一票失效。
3. **风险 C：授权过宽/过窄**——防线 = §2 只授"调度与过程裁决"，§5.d 的
   90 天不使用自然过期，§5.2 的修订通道保持条款可校准。

## 2. 适用范围：captain 可自主推进的事项（授权内容）

以下事项在**明示边界内**由 captain 自主调度与过程裁决，免除逐项请示义务
（即对下列事项有条件豁免 AGENTS §1.7 的质问义务）：

1. **工程实现任务**（不改研究语义者）：在任务 inScope、既有已批准契约与
   RED 先行纪律内，自主派发、验收、闭环；不含任何语义/契约/数据/运行态
   决策（那些见 §3）。
2. **治理文档与审计类任务**（docs-only）：审计报告、测量日志、治理台账
   收敛、批准记录**按已获授权的补记规格**落盘（如 Q4① 之 t38 模式：规格
   由用户裁决给出，captain 核对规格后派发）。
3. **任务台账运维**：claim/完成/依赖收敛、任务行与分支历史对账、repair
   闭环管理（review 判红后的修复轮派发）。
4. **契约草案的起草派发**：派发起草任务与选定起草人——起草本身不是批准
   （批准见 §3.2）。
5. **复审调度**：评审任务的派发、复审轮次管理、评审材料定位。

**权限性质声明（本条的边界，与 §3 等权）**：以上授权 = 调度权与过程裁决权；
不包含任何"批准权"。凡属 §3 列举的事项，captain 的角色是**准备材料并转达
用户**（草案/证据/选项清单），拿到用户明确裁决原文后才可执行；无原文时任务
保持等待态（G0 流程中 t35 的"核实性 noop 等待"即为标准姿态）。

## 3. 硬边界：仍逐项用户批准，captain 不得自主推进或批准

1. **研究语义变化的批准**（AGENTS §3.2 全项：特征/算子定义、可用时间、
   grammar、标签、horizon、rebalance、Reward、搜索空间与预算、seed pairing、
   股票池、PIT mask、数据 tier、组合/费用/成交/统计检验/晋级阈值等）。
2. **预注册契约的批准**（含 DRAFT→APPROVED 状态变更；含对既有契约批准的
   追认与勘误批准；含 p17 类数据底座契约）。
3. **正式 research/promotion 运行**与预算放行（AGENTS §4.1 三种运行的
   promotion 级；engineering 类验证不在其列）。
4. **生产数据落地**：任何 DB 回填、迁移、purge、删除或有状态窗口操作
   （AGENTS §5.6；含 ashare_v2 类新库回填的启动）。
5. **push / 远程 PR / merge / 发布**等外部状态变更（AGENTS §2.1.1）。
6. **本授权条款自身的批准、修订与失效裁决**（§5.2）。

**处置方式**：命中硬边界的任务，captain 按"材料齐全 → 转达 → 等原文 →
按原文执行"处理；无用户明确裁决原文时禁止推进，禁止以沉默、赶进度或
"本地看起来正常"替代批准（AGENTS §1 原文重申）。

## 4. 批准记录回写义务（本条款的核心新增，补偿验证要素）

1. **触发判定**：契约满足"实现已合入生效"（实现 commit 在 main 可查，且
   运行路径已消费其语义/常量）时，其批准记录**必须在实现合入的同一流程
   窗口内回写**——起草（预注册）→ 批准 → 实现 → 回写，四步缺一不可。
2. **记录要素与形式**：按 p16 先例（commit `2f5e18b` 模式）——契约文件头
   批准行 + 批准节记录；要素 = 批准人、批准日期、批准原文或授权来源、
   git 可查时序（预注册 commit → 批准证据 → 实现 commit）；CONTRACTS.md
   索引只加指针、不作状态裁决。
3. **缺失的后果（fail-closed）**：批准记录缺失的契约 = 治理阻断项——阻断
   其后续正式运行消费（formal runs、promotion、paper 不得引用该契约语义），
   直至补记完成；补记批准本身属 §3.2 硬边界，需用户追认授权。
4. **审计触发**：governance-auditor 或 reviewer 在任何任务中发现"实现生效
   但批准记录缺失"，按 G0 审计模式（`docs/g0_approval_evidence_audit.md`）
   整理问题清单交 captain 转达用户，**不得静默补写**。
5. **回写豁免**：无。任何"进度紧急""实现已经生效"不构成豁免理由——
   恰恰是生效本身使回写成为义务（生效越久，缺口越接近 §1.2 风险 B）。

## 5. 失效条件与修订方式

### 5.1 失效条件（任一命中即失效，无需另行裁决）

1. **用户明示撤回**授权（任何渠道的明确撤回原文）；
2. **captain 硬边界违规一次即失效**：captain 自主批准了 §3 任一项且经用户
   确认——自主权冻结，待用户新裁决（不因"结果正确"豁免：本条款约束的是
   授权边界本身）；
3. **团队终局不延续**：本团队解散/任务终结后，授权不跨团队自动延续，除非
   用户在新团队指令中明示重授；
4. **90 天不使用自然过期**：批准后 90 天内无任何依本条款的自主推进记录，
   视为过期，需重新批准。

### 5.2 修订方式

1. 修订 = 新草案起草（§2.4 范围内派发）→ **用户批准**（§3.6）→ 旧版文件
   头标注 superseded 并指向新版；修订期间自主权按旧版继续有效，直至新版
   批准或旧版失效。
2. 修订不得放宽 §3 硬边界清单与 §4 回写义务——这两节是本条款的存在理由；
   若用户要求放宽，属新授权，须全量重新起草并批准。

### 5.3 冲突与仲裁

1. 本条款与 AGENTS.md 冲突时，**收紧从严**：授权不得放宽 AGENTS 任何
   "必须/禁止"硬门禁；本条款仅在 AGENTS §1 末段"流程例外由用户明确授权"
   框架内生效。
2. 仲裁顺序：用户本次明确要求 > 本条款（批准后）> 已批准契约 > 契约测试 >
   实现 > 测量日志（与 AGENTS §1 一致，本文不改变它）。
